# 判断を残し、次の仕事で使う: 分業方針と確認資産の接続

今回の追加は実装済み・未実行です。CLIテストと実モデル呼び出しは行っていません。

## 原点

AIとの仕事を、会話の保存やニュースレターだけで終わらせません。
人間の判断、適用条件、検証方法、失敗例が、次の仕事で同じ判断を買い直さずに済む資産になることを目指します。

人間の保有水準 OWN / REVIEW / REFERENCE / DELEGATE と、
システムが実行できることは独立です。
OWNを選んだだけでAIを禁止せず、DELEGATEを選んだだけで実行を許しません。
理解の証拠がまだないことも、その人が理解していないことの証明にしません。

AIは候補生成器です。自己評価や二役の同意を、実行結果、利用者の承認、独立した証明へ昇格させません。
モデルを替えても、既存の台帳、出典、確認契約、今回の分業方針は残ります。

## 今回実行側へ接続したもの

skills-policy-set は、記録済みの技能に次の分業方針を結び付けます。
記録は追記型で、以前の判断と理由を消しません。

- 対象プロジェクト、run、技能ID、その技能の出典。
- AIへの担当範囲 explain / propose / check。
- 再利用時の確認方式 confirm / assisted / auto-check。
- 許可する資産IDの明示的な一覧。
- 許可するファイルパスの明示的な一覧。
- 人間がその範囲を選んだ理由。

この版の実行対象は、既存の有限述語による確認契約だけです。
任意のコード、シェル、ネットワーク操作、ファイル編集は許可しません。

explain は参照のみ、propose は確認案の提示まで、check は条件を満たした確認実行までです。
この範囲指定は skills-route / skills-reuse の入口で強制します。
既存の work や skills-build を含む全コマンドの包括的な実行ポリシーではありません。
コード生成・編集の権限を技能ごとに拘束する接続は、まだ別の実装範囲です。
既存の署名・権限管理は解除しません。これは同一OS利用者に対する防御でもありません。

## 使う順番

以下の LIB は設定済みの個人ライブラリです。
RUN、SKILL、ASSET、CLAIM は実際の記録から選ぶIDです。サンプルの文字列をそのまま実行するものではありません。

~~~sh
verantyx --project "$LIB" skills-stack --run "$RUN"
verantyx --project "$LIB" skills-policies --run "$RUN"
~~~

一覧が返した方針の revision を使って、対象を明示して登録します。
ASSET は保存済みの確認契約です。単なるAIの文章や取り込んだ原文は実行契約になりません。

~~~sh
verantyx --project "$LIB" skills-policy-set "$RUN" \
  --candidate "$SKILL" \
  --ai-mode check \
  --reuse-mode assisted \
  --path result.json \
  --asset "$ASSET" \
  --reason "この技能に関連する既存の確認契約を、このファイルの確認に限って利用する。" \
  --expected-policy-revision "$POLICY_REVISION" \
  --key policy-01

verantyx --project "$LIB" skills-route "$RUN" \
  --candidate "$SKILL" --asset "$ASSET" \
  --claim "$CLAIM" --target result.json
~~~

skills-route は読取専用です。方針、ファイル、資産、主張を照合し、
参照のみ、案の提示のみ、確認待ち、実行候補、不明、範囲外を区別して返します。
対象ファイルを観測するので、この入口では既存の選択ファイル制約も適用されます。

経路が返した scope ID に限定して実行します。

~~~sh
verantyx --project "$LIB" skills-reuse "$RUN" \
  --candidate "$SKILL" --asset "$ASSET" \
  --claim "$CLAIM" --target result.json \
  --scope-id "$SCOPE_ID" --confirm-scope "$SCOPE_ID" \
  --key reuse-01 --execute
~~~

--execute がない場合は経路の表示だけです。
実行する場合も、既存の確認契約をコピーして既存の検証経路へ渡します。
新しい期待値の生成、ソース契約の書換え、自動修復ループ、モデル呼び出しはありません。

## 三つの確認方式

- confirm: 毎回 --confirm-scope と --judgment-reason を指定する。今回適用する理由も記録に残す。
- assisted: 保存済みの方針を使い、今回の範囲IDを --confirm-scope で確認する。理由の再入力は不要。
- auto-check: 保存済みの範囲内では追加の確認入力を求めない。ただし --execute、最新の --scope-id、通常の権限条件は必要。

auto-check は、常駐監視や無制限の自動実行を開始する設定ではありません。
方針の変更も明示的な新しい登録です。同じキーによる再送で方針や実行内容を上書きしません。

## 範囲を拡大しない

経路の範囲IDには、方針の版、技能の出典、runの版、資産ID、主張ID、対象パス、
観測したファイルと判断情報を含むコンテキストのハッシュを結び付けます。

初回実行はこのコンテキストの一致を既存の資産ワークフロー側でも要求します。
方針や内容が変われば、新しい状態を選び直します。
途中からの再開は既存の実行記録に従い、完了済みの同じキーを再送しても確認を新規実行しません。
「以前同じようだった」という意味の近さから、対象や適用条件を推測して広げません。

## 学習と資産

skills-stack は技能の四分類に加えて、関連する分業方針を表示します。
技能の保有目標、AIへの担当範囲、記録済みの確認契約、実際の結果は別々に残ります。
分類を変更しただけで確認契約の合格状態や実行権限が変わることはありません。

確認が失敗しても、期待値をAIに作り直させて成功扱いにしません。
成功はその契約・対象についての結果であり、一般的な正しさや人間の習得認定ではありません。

## 構造体

経路は出典、許可範囲、対象となる主張、反例、方針、未実行の結果を六方向に関連付けて返します。
実行前の条件照合に用いる情報と、表示する関係を同じ経路結果に保持します。
矛盾や不足を合意で埋める仕組みにはせず、不明または停止として残します。
これは明示IDと条件に基づく決定論的な経路であり、学習済みの意味ルーティングではありません。

## 次の範囲

コード編集側へ同じ分業方針を接続すること、
実行履歴から次回の技能説明を補強すること、
他プロジェクトへ移す際の明示的な適用条件の再設定が残っています。

既存の方法を使い回す導線を先に作り、モデル呼び出しの回数やテストの数を増やすこと自体を成果にしません。
