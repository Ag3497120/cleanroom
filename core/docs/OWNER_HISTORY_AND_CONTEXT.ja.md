# Owner履歴・待ち時間・文脈と整理の費用

2026-09-18。Cleanroomのローカル実装についての説明です。

## Ownerの保存と検索

同じOwnerノートに紐づく全Agent会話の依頼、途中の回答、最終回答、追記、Ownerへの質問の返答、実装中の学習メモ、本人のメモ・判断、学習番号への質問と回答を履歴として表示します。別のOwnerノートの会話は混ぜません。

保存済みの原文は削除・要約で置換せず、表示は200項目ずつです。端までスクロールすると次のページに移動します。検索は表示中のページだけでなく、そのノートに属する保存済み全体を対象とします。空白区切りの語はAND検索、全角・半角と大文字・小文字を正規化します。`%` や `_` は検索用のワイルドカードとして扱いません。

Owner検索欄に入力すると、該当する記録の本文に行番号と `▶`、背景色を付けます。前後の行も残します。EnterまたはF8で表示中の次の該当行、Escに続けてF8で前の該当行へ移動します。

保存・画面表示・AIへの送信は別です。Owner履歴全体をプロンプトへ追加する変更ではありません。Agent入力で明示的に選んだ参照は従来どおり原文を展開します。個人プロフィールやMy skillsは既存の共有設定に従います。このCodexアプリ内の会話をCleanroomへ自動取り込みする機能でもありません。`//` の揮発的な対話は既存の非保存方針を維持します。

## Ollama / LM Studio

新規のOllama接続、ループバックのOpenAI互換接続は既定1800秒（30分）、設定上限7200秒（2時間）です。外側のモデルプロセスには終了処理用の5秒を追加します。一般の外部コマンド・ツールの実行時間制限を一括で伸ばす変更ではありません。

既存API接続の設定値は保持します。既存のローカル接続を選択した状態で次を実行すると、待ち時間を変更できます。

```text
/timeout 1800
```

ターミナルからは以下です。

```sh
verantyx --project /path/to/project model-timeout 1800
```

元の接続ファイルを上書きせず、新しい設定を保存して選択します。思考モード・コンテキスト長・接続先は保持します。モデルのダウンロード、起動、追加のAI呼び出しは行いません。新規の `model-api-config --timeout` でも明示指定できます。

Ollamaの思考ストリームは継続して表示し、最終応答の入力・出力トークン報告も利用量集計に含めます。LM Studioの互換APIは現在も最終JSON応答を待つ方式です。待ち時間を伸ばしても、出力トークン上限やメモリ不足を解消するわけではありません。

## 文脈の表示

入力欄の下に、直近に準備したWork依頼で大きい項目を1行表示します。詳細は `/context`、ターミナルでは `verantyx context-usage`。指示、スキル、会話、ツール定義、ツール結果、共有済み個人記録などを分けます。

これは**JSONのUTF-8バイト比率**です。モデル別のトークン比率、コンテキスト上限の消費率、スキルを実際に使った頻度ではありません。本家CLI側に保持される会話やプロバイダーの追加指示も含みません。準備した依頼の内訳であり、送信成功の証拠でもありません。未取得の値を0にしません。本文は診断ファイルに複製せず、分類別の数値・準備時刻・作業IDなどだけを保存します。

実測トークンとキャッシュの報告は `/usage` / `verantyx model-usage` です。文脈の構成比とキャッシュ命中率を同じ数値として扱いません。

能力を採点する表示ではなく、本人がAIへの情報の渡し方と費用を理解するための表示です。Cleanroomの思想と両立します。

## 番号付きの記憶とスキル

現状の `L-000123` は実装中に残した学習メモへの参照番号です。Owner入力で挿入する参照トークンも、記録のID・版・原文に紐づきます。番号そのものが詳細な記憶をモデルへ復元する圧縮形式ではありません。Agentへ参照を渡す際は本文を展開するので、その分の入力は発生します。

既存のMy skillsは、目的・入力・手順・適用条件・止める条件・確認方法・出典を持つ再利用用のAI手順です。本人の習得状態、実行権限とは別に扱います。現在のプロンプトには、共有対象のスキル本文を件数・サイズ制限の範囲内で含めています。すべてが「短い索引だけを渡し、必要時だけ本文取得」という構造になったわけではありません。

効果が期待できる設計は、原文を保持したまま「短い索引 → 選んだ記録・手順の本文 → 根拠の原文」と必要な分だけ取得する形です。反復して使う手順にはスキルが適します。一度だけ起きたこと、当時の判断理由、私的なメモは、そのまま履歴として保存する方が意味を保てます。全部を毎回スキルへ変換して全文投入すると、整理の出力と次の入力が増える可能性があります。

既存の会話要約は、原文の出典と被覆範囲を保存し、直近の会話や権限を残しながら古い文脈を短くします。`read_work_history` による原記録の取得もあります。要約は非可逆なので、正確な細部は原文で確認する必要があります。

## 整理するたびにトークンを使うか

| 処理 | 追加の独立したAI呼び出し | 現状 |
|---|---|---|
| 生の会話・イベント・Ownerメモの保存 | なし | ローカル保存 |
| 検索・ページ送り・Atlas表示・文脈内訳計算 | なし | ローカル処理 |
| Work応答内の `learning_notes` | なし | 同じ応答の出力トークンは増える。モデルが出力した内容と出典を取り込む |
| 作業後のReflection・スキル候補整理 | あり | このMacの対象プロジェクトは `off`。手動の整理ではWorkモデルを利用可能 |
| 個人向けの成長レポート | 条件付きであり | 個人機能・共有・モード・アダプタの条件が揃う場合。ローカルの事実保存とは別 |
| Unpackの新規解説 | あり | 明示的に解説を作るとき。保存済み解説の閲覧は呼ばない |
| `/compact` / 自動会話要約 | あり | 未要約の記録を処理し、保存済み要約を再利用。自動処理は1回の準備で最大2呼び出し |

したがって「毎メッセージの後に別のLLMで全記録を整理し直す」仕組みではありません。このMacの対象プロジェクトでは自動要約もoff、個人記録は有効・AI共有はoff・整理モードはon_demandでした。これらの設定は維持しています。ただし、Workの出力内の学習メモにも費用はあり、自動要約を有効にした場合や、整理を明示的に実行した場合には追加の利用が発生します。Reflectionをoffにすると、自動でのスキル候補整理も減ります。

## キャッシュ効率

既存のネイティブCLIのセッション継続・差分送信に加えて、直APIの共通プロトコル・ツール定義を依頼固有のファイル範囲や本文より先に配置しました。新しいrun IDだけでOpenAIのルーティングキーが変わらないようにし、共通部分・作業文脈・完了済みツール結果に最大4個のキャッシュ境界を置きます。元のJSONは損失なく再現できます。

本家と同等の仕組みを使うことと、同じ命中率・請求額になることは別です。キャッシュの最小長・保存期間・モデル・時間間隔・サーバー側の処理、Cleanroom固有の契約や追加整理によって結果は変わります。対応コードとオフラインテストだけで「本家と同額」を保証しません。同じモデル・課題・間隔で報告された入力、キャッシュ読み取り／書き込み、出力、整理回数を比較する必要があります。

## CLIとAtlas

CLIで実装・質問・説明・本人の記録まで完結し、Atlasを広い画面での振り返りに使う方針を勧めます。操作と記録の入口が分かれにくく、学習のための画面移動を必須にせずに済みます。

Atlasでは、手順の配列や入れ子の情報を読みやすく表示し、元の作業記録を個別に開閉・検索できるようにしました。要約・詳しい解説・元資料の切替は維持します。元JSONも確認できます。閲覧によって本人の習得状態が変わることはありません。
