# 来歴を中心にしたCLI MVP: 0.7.5rc2

## 目的

Veraは、AIが実装の大部分を担う開発において、人間がプロジェクトの所有者・理解者・開発者であり続けるための共同開発基盤です。分類器や事前審査を主役にしません。

意味の解釈は選択したAIが行います。違う回答や違う分類は、それだけでは失敗ではありません。同じ回答でも問題ありません。コードが強制するのは回答の一致ではなく、記録の結び付き、権限、版、出典、人間の選択の区別です。

## 実装の変更

1. 新しい整理にはgeneration_idを付け、同じ作業内容でも以前のAI回答へキャッシュ固定しない。
2. 同一キーの再送は同一操作の再表示とし、二重課金・二重実行を避ける。
3. 整理の自由な観点をperspectiveとして保存する。モデル、元イベント、時刻、人間の選択を追跡する。
4. 以前の未選択の見方もPerspectivesから開ける。通常のOwner欄は最新候補と人間が関わったものに絞る。
5. 後から追加された共有メモ・人間の選択・実検査を、新しい整理の文脈に含める。私的メモは含めない。
6. 人間が指定した検査コマンドを候補コピーで実行し、結果をWorkとは別のイベントにする。
7. 通常Workに対するownershipコマンドを専用表示へ接続する。
8. 利用できないCodexモデルを、課題の分類失敗や不明なJSON不一致と混同しない。

## 検査コマンドの境界

実行は明示的な確認を必要とします。生成したコードは任意のOS操作を含み得るため、コピーしたディレクトリや環境変数の削減だけをサンドボックスと呼びません。ネットワークやユーザーファイルへのアクセスはOS権限に依存します。

APIキーを除いた環境、使い捨てのHOME、保存候補のコピー、時間制限、出力制限、プロセスグループ停止を使います。本体への採用や外部公開は行いません。生成AIへrun_checkという任意実行ツールは公開していません。

## 公開判断に必要な証拠

回答の文章や分類テーマを固定した正解にはしません。次を受入項目とします。

- 選んだ実モデルで候補と回答を保存できる。
- 異なるテーマでも、同じホスト処理を通る。
- 新しい整理が実際に別の呼び出しとなる。
- 整理失敗時にも作業結果が残る。
- 以前の見方と、人間が選んだ関わり方が残る。
- 次の作業・再整理で共有した判断や理解方針が参照される。
- 私的メモをモデル入力へ混ぜない。
- 成功・失敗・タイムアウトの検査記録が区別される。
- AIの検証主張や学習分類だけでは、検証済み・習熟済み・有効規則にならない。
- CLIの起動、設定、ノート表示、JSON操作、配布パッケージを確認する。

有限の試験を通っても、一般性能100%や人間の経験喪失を必ず防ぐことの証明にはしません。実モデル名・テーマ・結果・未確認事項を試験レポートに残します。

## 外部コントリビュータへ分けられるもの

- OS別のコンテナ・サンドボックス実行バックエンド。
- ローカルモデルと各プロバイダーの接続試験。
- 別Mac・Linux・各端末サイズ・アクセシビリティの互換性。
- IDE側の候補比較、署名、配布。
- 大規模コーパスの索引・圧縮・明示的な文脈選択。

中核として維持するのは、仕事が進み、人間の判断と経験が残り、次の仕事に使われる循環です。
